The one bridge

Plan and Reality never touch each other directly. The only thing they share is the catalog exercise — which is why it sits between them here.

That is why progress survives any change of plan: exercise_record points at the exercise, never at the routine. Rename a routine, delete it, switch weekly trainings mid-week — the history is untouched.

Two names, on purpose

routine_session carries both routine_id and a routine_name snapshot, while routine_exercise deliberately stores no name at all.

They are different kinds of thing. A routine exercise is a live part of a plan, so it must always show the current catalog name. A finished session is a historical fact: "on Monday you trained Espalda y bíceps" stays true after you rename or delete that routine.

Not stored — these are queries

  • Session duration — ended_at − started_at
  • Chart point — max(weight_kg) per date, per exercise, per user
  • Heaviest-weight record — max(weight_kg) over all of that user's sets
  • Previous-session prefill — the latest exercise_record for that user and exercise

Invariants the schema can't hold

  • A weekly_training always has exactly 7 day rows, created in the same transaction as its parent
  • exercise.primary_muscle_subgroup_id must belong to the same muscle group as the exercise — needs a trigger or an application rule
  • Only the current day can be logged, and a blank set is never written
  • Undecided: nothing stops two sessions on the same date. If one per day is the rule, it needs a unique index
